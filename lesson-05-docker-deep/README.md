# Урок 5. Docker вглубь: многоэтапная сборка и оптимизация

## Цель урока
Научиться уменьшать размер Docker-образов с помощью многоэтапной сборки (Multi-stage build), управлять слоями и работать с томами (volumes) для сохранения данных.

## Что потребуется для этого урока
* **Сервер или локальная машина с Docker**.
* **Проект на Java (Spring Boot)**, который мы собирали ранее (или любой другой `.jar` файл).
* **Dockerfile** из предыдущих уроков (мы его перепишем).

---

## Теория

### 1. Проблема «толстых» образов
В прошлом курсе мы использовали простой `Dockerfile`:
~~~dockerfile
FROM eclipse-temurin:21-jdk-alpine
WORKDIR /app
COPY target/backend-app.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
~~~
Этот образ содержит **полный JDK** (около 300–500 МБ), а для запуска приложения достаточно **JRE** (около 100–150 МБ). 
Чем больше образ, тем дольше он скачивается и занимает место на сервере.

### 2. Многоэтапная сборка (Multi-stage build)
Docker позволяет использовать несколько базовых образов в одном `Dockerfile`.
* **Первый этап (build):** берем полный JDK, компилируем проект.
* **Второй этап (run):** берем только JRE и копируем туда готовый `.jar` из первого этапа.

Пример:
~~~dockerfile
# Этап 1: Сборка (используем Maven и JDK)
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

# Этап 2: Запуск (используем только JRE)
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /app/target/backend-app-0.0.1-SNAPSHOT.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
~~~

* `AS build` — дает имя первому этапу.
* `COPY --from=build` — копирует файл из первого этапа во второй.
* В финальный образ попадает **только** готовый `.jar` и JRE, без Maven и исходного кода.

### 3. Слои и кэширование
Каждая инструкция в `Dockerfile` (`RUN`, `COPY`, `ADD`) создает новый слой. Docker кэширует слои, чтобы не пересобирать всё заново.
**Правило:** сначала копируйте то, что меняется редко (например, `pom.xml`), а потом то, что меняется часто (исходный код `src`).

В примере выше:
1. Сначала копируется `pom.xml` и запускается `mvn dependency:go-offline` (скачиваются зависимости).
2. Только потом копируется `src` и собирается проект.
Если вы измените только код в `src`, Docker не будет заново скачивать зависимости.

### 4. Тома (Volumes)
Контейнеры эфемерны: если контейнер удалить, все данные внутри него исчезнут.
Чтобы сохранить данные (например, базу данных или логи), используются **тома**.
Том — это папка на хост-машине, которая подключается к контейнеру.

Пример в `docker-compose.yml`:
~~~yaml
services:
  db:
    image: postgres:16-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data
volumes:
  postgres_data:
~~~
* `postgres_data` — это именованный том. Docker создаст его автоматически.
* Данные сохранятся даже после `docker-compose down`.

### 5. Переменные окружения и секреты
**Переменная окружения** — это значение, которое задается в операционной системе (или в Docker) и доступно программам во время их работы. Это как глобальная настройка, которую программа читает при запуске.

Зачем они нужны:
* **Безопасность:** Пароли, токены и ключи не должны храниться в коде или в `Dockerfile` (иначе они попадут в Git и станут видны всем).
* **Гибкость:** Один и тот же Docker-образ можно запустить на разных серверах, передав разные настройки (например, разные пароли к базе данных).

Пример файла `.env` (в нем хранятся секреты, он **не** добавляется в Git):
~~~env
DB_PASSWORD=supersecret
~~~

В `docker-compose.yml` мы ссылаемся на эту переменную через `${...}`:
~~~yaml
environment:
  POSTGRES_PASSWORD: ${DB_PASSWORD}
~~~

*Примечание:* В Java-коде переменные окружения читаются через `System.getenv("DB_PASSWORD")`, а Spring Boot автоматически подхватывает их, если они названы в формате `SPRING_DATASOURCE_URL` и т.д.
