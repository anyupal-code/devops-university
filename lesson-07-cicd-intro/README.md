## Теория

### 1. Проблема ручной сборки
Представьте, что над проектом работает команда из 5 человек. Каждый день они пишут код, делают коммиты и пушат в GitHub. 
Раньше процесс выглядел так:
1. Разработчик пишет код.
2. Вручную запускает тесты на своем компьютере.
3. Вручную собирает `.jar` файл.
4. Вручную копирует файл на сервер.
5. Вручную перезапускает приложение.

Это долго, нудно и чревато ошибками (забыл запустить тесты, скопировал не тот файл, упал сервер).

### 2. Что такое CI (Continuous Integration)?
**Непрерывная интеграция** — это практика, при которой разработчики часто (несколько раз в день) сливают свой код в общую ветку. 
Каждый раз, когда код попадает в репозиторий, **автоматически** запускаются:
1. Сборка проекта (компиляция).
2. Запуск тестов (юнит-тестов, интеграционных).
3. Проверка стиля кода (линтеры).

Если тесты упали — разработчик сразу узнает об этом и исправляет ошибку, пока она не попала в продакшн.

### 3. Что такое CD (Continuous Delivery / Deployment)?
* **Continuous Delivery (Непрерывная доставка):** код автоматически собирается и тестируется, а затем готов к деплою (но деплой запускается вручную нажатием кнопки).
* **Continuous Deployment (Непрерывное развертывание):** код автоматически деплоится на сервер без участия человека (если все тесты пройдены).

### 4. Конвейер (Pipeline)
Весь процесс CI/CD называется **конвейером** (pipeline). Он состоит из последовательных этапов (этапов может быть больше):
1. **Build (Сборка):** `mvn clean package`.
2. **Test (Тестирование):** `mvn test`.
3. **Package (Упаковка):** сборка Docker-образа.
4. **Deploy (Развертывание):** отправка образа на сервер и перезапуск.

### 5. Инструменты CI/CD
Самые популярные инструменты:
* **GitHub Actions** — встроен в GitHub (мы будем использовать его).
* **GitLab CI** — встроен в GitLab.
* **Jenkins** — старый, мощный, но сложный в настройке (требует отдельного сервера).
* **CircleCI**, **Travis CI** — облачные сервисы.

### 6. Как работает GitHub Actions?
В корне репозитория создается папка `.github/workflows/`. 
Внутри лежат файлы с расширением `.yml` (YAML). Каждый такой файл — это один конвейер (workflow).

Пример простого workflow (файл `.github/workflows/build.yml`):
~~~yaml
name: Build and Test

on:
  push:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v4
    - name: Set up JDK 21
      uses: actions/setup-java@v4
      with:
        java-version: '21'
        distribution: 'temurin'
    - name: Build with Maven
      run: mvn clean package
~~~

* `on: push` — запускать при каждом пуше в ветку `main`.
* `runs-on: ubuntu-latest` — выделенная виртуальная машина с Ubuntu.
* `steps` — шаги, которые выполняются последовательно.
* `actions/checkout` — копирует ваш код из репозитория на виртуальную машину.
* `run` — выполняет команду в терминале.
